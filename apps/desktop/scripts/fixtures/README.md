# Smoke Test Fixtures

## Purpose
Small static JSON fixtures used by scripts in the parent `scripts/` folder, so smoke tests don't need a live
Firebase project or web app running to exercise the local judge.

## What This Folder Owns
- `trapping-rain-water-judge-data.json` - a `CodingProblemJudgeData` payload (the exact shape
  `GET /api/coding-problems/:id/judge-data` returns - see `apps/web/src/lib/coding-catalog/types.ts`) for the
  "Trapping Rain Water" problem: per-language harness (`prefix`/`suffix`), starter code, visible tests, and hidden
  tests. `smoke-coding-arena.js` serves this from a tiny in-process HTTP mock instead of hitting a real web app.

## Regenerating this fixture
If `apps/web/src/lib/coding-catalog/problem-builder.ts` or `public-shapes.ts`'s `toJudgeData()` changes shape, this
fixture goes stale silently (the smoke test would keep "passing" against the old shape). Regenerate it by running
`buildCodingProblemRecord()` + `toJudgeData()` against the `"trapping-rain-water"` entry in the root
`/coding-problems.seed.json`, and overwrite this file with the JSON.stringify'd result. Since those two files are
TypeScript and this fixture is generated by a one-off Node script rather than a checked-in build step, there's no
single command to run - transpile `problem-builder.ts` and `public-shapes.ts` to CommonJS with the `typescript`
package already in `node_modules` (`ts.transpileModule`), `require()` the result, and write out
`toJudgeData(buildCodingProblemRecord(input, { createdBy: "fixture-gen", order: 1 }))`.

## Maintenance Notes
This is test data, not app data - it is never imported by anything under `src/`, only by scripts in the parent
folder.

## Contributor Checklist
1. Keep changes scoped to this folder responsibility before reaching into adjacent modules.
2. If you add a fixture for a new problem, name it `<problem-id>-judge-data.json` to match this one's convention.
3. Prefer additive changes over breaking renames, and document any migration impact clearly.
